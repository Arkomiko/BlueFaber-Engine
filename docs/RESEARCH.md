### PluginBlueprint — ближайший кандидат для переиспользования

Версия 2.2.0 в проверенном коммите ориентирована на Paper 26.3 и JDK 25. В пользовательском сценарии есть типизированные соединения, подграфы, команды и события, проверка перед сборкой, Java и JAR на выходе, тестовый сервер и навигация к узлу по ошибке компиляции. Миграция проекта из первой версии относится к формату PluginBlueprint. Для импорта произвольного JAR потребуется собственный анализ. Лицензия BSD-3-Clause. [Репозиторий](https://github.com/InventivetalentDev/PluginBlueprint), [сценарий и требования](https://pluginblueprint.net/)

Проверенный коммит `969e5e2402341e7d504dc343d6e5c06770b0f014` даёт конкретные точки интеграции.

- `src/lib/codeGenerator.ts` принимает граф LiteGraph либо его представление для генерации, разворачивает подграфы, обращается к каталогу классов и выпускает `GeneratedPlugin extends JavaPlugin`. Есть отдельные обработчики событий, методов, конструкторов и встроенных узлов. Из этого кода стоит проверить точечное заимствование для адаптера Paper. [Генератор](https://github.com/InventivetalentDev/PluginBlueprint/blob/969e5e2402341e7d504dc343d6e5c06770b0f014/src/lib/codeGenerator.ts)
- `src/lib/nodeGenerator.ts` связывает каталог типов с LiteGraph и правилами соединения портов. Генератор каталога в `tools/classdata` использует Java Doclet. Для BlueFaber это пример получения подписей и типов узлов из API. Индекс classfile нужен отдельно для зависимостей без Javadoc и для анализа без загрузки исследуемых классов. [Генерация узлов](https://github.com/InventivetalentDev/PluginBlueprint/blob/969e5e2402341e7d504dc343d6e5c06770b0f014/src/lib/nodeGenerator.ts), [генерация каталога](https://github.com/InventivetalentDev/PluginBlueprint/tree/969e5e2402341e7d504dc343d6e5c06770b0f014/tools/classdata)
- `src/lib/javaCompiler.ts` запускает внешний `javac`, передаёт уровень Java и classpath и пакует JAR. Проверка графа и компиляция разведены. Этот подход пригоден для сравнения с отдельным JVM-процессом BlueFaber и версионированным протоколом диагностик. [Проверка графа](https://github.com/InventivetalentDev/PluginBlueprint/blob/969e5e2402341e7d504dc343d6e5c06770b0f014/src/lib/graphValidator.ts), [компиляция и упаковка](https://github.com/InventivetalentDev/PluginBlueprint/blob/969e5e2402341e7d504dc343d6e5c06770b0f014/src/lib/javaCompiler.ts)

Сначала проверить адаптер на одном графе. Измерить объём кода для переноса, число зависимостей от LiteGraph и Paper и возможность обработки второго целевого профиля. При внедрении компонентов сохранить лицензионные уведомления. Поддержку Paper 1.21.1 из пилота BlueFaber проверить отдельно, поскольку в просмотренной реализации закреплён другой профиль.

### Kerlann/blueprint и PACO

**Kerlann/blueprint (MIT)** даёт самый близкий пример редактируемых игровых графов. Текст BScript обратимо связан с графом, а компилятор выпускает инструкции собственной виртуальной машины. У проекта есть типизированные порты, сохранение узлов с недоступными расширениями, отладка и каталог узлов. Fabric-версия предназначена для Minecraft 1.21.11. Модуль NeoForge описан как собирающийся и запускающийся, публикация в README не заявлена. [Репозиторий](https://github.com/Kerlann/blueprint), [спецификация BScript](https://github.com/Kerlann/blueprint/blob/1823ec47126c62eb327489da6d00b5f6cb238f1d/docs/bscript-spec.md)

В коммите `1823ec47126c62eb327489da6d00b5f6cb238f1d` компилятор ссылается на `net.minecraft.resources.Identifier`. Изоляция от конкретного загрузчика оставляет зависимость от классов Minecraft. Для переиспользования проверки графа или регистрации узлов в настольном инструменте понадобится отделить такие типы. Подход с дремлющими узлами стоит испытать в импорте расширений BlueFaber. [Компилятор графа](https://github.com/Kerlann/blueprint/blob/1823ec47126c62eb327489da6d00b5f6cb238f1d/core/src/main/java/fr/blueprint/core/compile/Compiler.java), [проверка графа](https://github.com/Kerlann/blueprint/blob/1823ec47126c62eb327489da6d00b5f6cb238f1d/core/src/main/java/fr/blueprint/core/graph/GraphValidator.java)

**PACO (MIT)** показывает независимый путь от визуальных блоков через TypeScript-модель к компилируемому Java. В README перечислены классы, интерфейсы, исключения, лямбды, потоки, `record`, `sealed` и switch-выражения. Сгенерированное окно Java доступно для чтения. Этот проект полезен для проверки Java-генерации и тестовых примеров, а импорт исходного Java и classfile требует отдельного контура. Проверен коммит `26daa79c173aed788bac3c937bf726f724793280`. [Проект и ограничения](https://github.com/PakoPakete/paco/tree/26daa79c173aed788bac3c937bf726f724793280), [тест генерации](https://github.com/PakoPakete/paco/blob/26daa79c173aed788bac3c937bf726f724793280/src/test/unit/javaGenerator.test.ts), [тест javac](https://github.com/PakoPakete/paco/blob/26daa79c173aed788bac3c937bf726f724793280/src/test/unit/javacCompile.test.ts)

Проверять селекторы и совпадения по байткоду целевого класса до запуска самого мода. [План проверки Mixin](PORTING.md) |

Сравнивать движки на одних и тех же классах, JDK, параметрах компилятора и точном classpath. Корпус должен включать вложенные и анонимные классы, bridge-методы, generics, лямбды и `invokedynamic`, `try-with-resources`, switch, records, preview-классы, multi-release JAR, удалённые debug-атрибуты и смешанные JVM-языки. Для каждого движка сохранять число восстановленных и компилируемых классов, полных пересборок, отличий в публичном ABI, отличий в наблюдаемом поведении, ошибок и тайм-аутов. Читаемость оценивать вручную на выбранной выборке. [Корпус и критерии восстановления](JAVA-RECOVERY.md)

Собственный компонент BlueFaber объединит обнаружение артефактов, подготовку classpath, движки декомпиляции, статический индекс, восстановление сборки и навигацию к исходной инструкции. Локальную доработку декомпилятора стоит делать после воспроизводимой ошибки и теста, который можно передать upstream. При наличии исходного проекта с подтверждённой версией его сборочные файлы и исходники дают лучший вход для сохранения авторской структуры.

## Проверки перед выбором компонентов

1. **Редактор.** В React Flow и адаптере PluginBlueprint собрать один фрагмент [Blusmor](BLUSMOR.md). Соединить руду с правилом добычи и сырым материалом, изменить результат, отменить изменение и повторно открыть проект. Подставить порт блока на вход предмета и проверить диагностику. Отдельно убрать и вернуть расширение с одним видом узла и сравнить сохранённые данные.
2. **Проверка независимого формата.** Переставить узлы, сохранить и сравнить поведение и сгенерированный Java. Подключить Fabric-экспорт из того же файла. Удержать стабильные ID узлов, портов и источников. Для актуального профиля Paper и пилотного 1.21.1 фиксировать результаты отдельно.
3. **Связь Java и графа.** Импортировать собственный мод без исходников. Открыть участок в графе, Java и инструкциях JVM, изменить одну ветвь и пересобрать на исходной версии. Unknown-узлы и неподнятые методы должны пережить сохранение проекта со своей привязкой к артефакту.
4. **Перенос.** Сравнить собственную реализацию с доступными Retromod и Sinytra на поддерживаемых ими комбинациях. Один стенд должен проверять переход namespaces, ремап вложенных библиотек, совпадение Mixin-селектора и отказ при неоднозначности. Записать требуемые зависимости, причины отказов и игровой результат.
5. **Производительность.** Зафиксировать машины, версии и параметры. Измерить p50 и p95 открытия графа, задержки соединения, сохранения большого проекта, длительность декомпиляции, пиковую память и отмену. Такой же протокол использовать для повторной оценки холста и движков после обновления версий. [Варианты автоматической раскладки](https://reactflow.dev/learn/layouting/layouting), [ELK с портами](https://github.com/kieler/elkjs)

## Условия переиспользования

Для подключения проверять лицензию на выбранном коммите, заголовки файлов, транзитивные зависимости и условия включения в дистрибутив. Для каждого заимствования фиксировать URL, SHA, перечень файлов, тип использования, необходимые тексты лицензий и уведомления. Отдельно учитывать код, параметры сборки, образцы модов, файлы mappings и игровые ресурсы. Поддержку API можно тестировать на разрешённых к использованию фикстурах и устанавливать нужные артефакты в локальный test runtime.
