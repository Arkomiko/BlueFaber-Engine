# Восстановление проекта из Java и JAR

Эта часть описывает импорт готовых модов и плагинов, реконструкцию проекта и выделение участков для визуального редактирования. Этапы реализации и поддерживаемые маршруты описаны в [карте разработки](ROADMAP.md) и [профилях переноса](PORTING.md).

## Что можно восстановить

JAR обычно содержит JVM-байткод, метаданные и ресурсы. Исходники, история проекта, комментарии, форматирование и сценарии сборки могут отсутствовать. Имена локальных переменных доступны, если компилятор сохранил соответствующие атрибуты. Часть типов остаётся в `Signature`, а выполнение использует в том числе стёртые сигнатуры. Для отдельных форм байткода точного выражения в Java может не существовать. Например, подстановка сложной динамической константы как обычного Java-выражения может менять момент вычисления. Храним оригинал, регистрируем такие случаи и показываем, какой материал удалось восстановить. [Формат class-файла JVM](https://docs.oracle.com/en/java/javase/26/docs/specs/jvms/jvms-4.html), [опции Vineflower для динамических констант](https://vineflower.org/usage/#decompile-complex-constant-dynamic)

| Вход | Приоритет и результат |
| --- | --- |
| Исходный Gradle или Maven проект | Открыть файлы и сохранить структуру модулей, языки и ресурсы. Сборка с пользовательскими скриптами выполняется отдельным действием. |
| JAR и соответствующий `sources.jar` | Сопоставить артефакты по версии, доступному хешу и классам. Использовать согласованный исходник, сопоставить сигнатуры и отметить расхождения. Пакет исходников может покрывать лишь часть результата генерации или shading. |
| Только JAR | Реконструировать новый проект по профилю сборки. Оригинальные скрипты, исходные Maven-координаты и настройки автора учитываются там, где их подтверждают файлы или внешние метаданные. |
| Обфусцированный, повреждённый или смешанный JAR | Извлечь инвентарь и читаемые части. Для неизвестных зависимостей, классов или преобразований сохранить точную причину и доступный оригинал. Для повреждённого контейнера зафиксировать, какие записи удалось прочитать. |

Состояние импорта хранится отдельно от факта сборки и проверки игры. «Открыт», «частично восстановлен», «собран для исходного профиля» и «проверен в игре» — самостоятельные результаты. Для экспорта на другую платформу действуют [отдельные проверки переноса](PORTING.md).

## Конвейер импорта

1. **Проверить и описать вход.** Прочитать каталог архива, определить SHA-256 исходника и каждой обработанной записи, зафиксировать имена и размеры. Ограничить число записей, распакованный размер и глубину вложения. Выявлять дубликаты имён, неоднозначность регистра в Windows, конфликт файла с каталогом, выход путей за пределы рабочего каталога, недоступный метод сжатия и ошибки целостности. Хранить вход как неизменяемый артефакт.
2. **Выдвинуть гипотезу о профиле.** Собрать доказательства из платформенных дескрипторов, манифеста, версий class-файлов, ссылок на платформенные пакеты, файлов Mixin и mappings. Представлять допустимый диапазон версий и кандидатов с уликами. Если JAR годится под несколько профилей, пользователь выбирает точную версию перед сборкой. Поддерживать мультиплатформенные артефакты и вложенные модули.
3. **Построить индекс.** Читать классы, публичные сигнатуры, аннотации, записи о вложенности, Maven-метаданные, ресурсы и декларации зависимостей без загрузки классов. Разделять зависимости исполнения, компиляции и обработки исходников. Для каждой найденной зависимости сохранять источник, диапазон, точную разрешённую версию и хеш. Если артефакт недоступен или найден только по косвенным признакам, показать это в отчёте.
4. **Подготовить JDK, classpath и mappings.** Сначала собрать окружение для исходной версии игры и загрузчика, включая правильную сторону. Для ссылок JVM хранить сырое и читаемое имя. Связывать класс по внутреннему имени, а член также по имени и JVM-дескриптору. Добавлять в индекс пространство имён, профиль и слой multi-release JAR. Для поиска переименований использовать mappings, правила API и контекст вызова. [Форматы Mapping-IO](https://github.com/FabricMC/mapping-io/blob/dev/src/main/java/net/fabricmc/mappingio/format/MappingFormat.java)
5. **Декомпилировать единицы компиляции.** Передавать Vineflower зависимости как внешние входы. Группировать верхнеуровневый класс, вложенные и синтетические спутники по связи в class-файле. Записывать диапазоны байткода, линии декомпиляции, вывод инструмента и ошибки. При падении движка либо проблеме разбора или компиляции, подтверждённой после подготовки classpath, создать вариант через CFR. Разрешать вручную выбрать вариант рядом с просмотром байткода. [Библиотечный API Vineflower](https://vineflower.org/usage-code/), [примеры API CFR](https://github.com/leibnitz27/cfr_client)
6. **Собрать восстановленный рабочий проект.** Записать восстановленный Java и ресурсы, собственный сборочный шаблон для выбранной цели, свойства профиля и файл фиксации зависимостей. В отчёт включить распознанные части, использованные шаблоны, неразрешённые ссылки, сохранённый байткод и файлы, добавленные вручную. Звенья происхождения должны вести от результата к записи JAR, затем к классу, методу и диапазону инструкций.
7. **Проверить экспорт на исходной цели.** Сначала проверить Java, метаданные и зависимости. Затем провести чистую сборку в закреплённой среде и проверить JAR и игру. У исходного JAR нет места в classpath финальной сборки. Если отдельные классы перенесены бинарно по явному правилу, включать только заявленные классы и выделять их в статистике. Компиляция с заглушкой отсутствующей зависимости пригодна для диагностики.
8. **Предложить подъём логики в граф.** Проанализировать восстановленные единицы и JVM-индекс, построить типизированное представление потока и поднять известные игровые операции. После принятия преобразования переназначить владельца фрагмента и проверить исходную цель повторно. [Владение фрагментами и формат графа](ARCHITECTURE.md)

Реконструированный проект открывается с читаемыми исходниками в `src/main/java` и ресурсами в `src/main/resources` для простого одномодульного проекта. Дополнительные модули, языки и стороны исполнения получают каталоги своего профиля. Вместе с проектом сохраняются версия конвейера, хеши, список входных артефактов и версионированный отчёт. Диагностика указывает, какую зависимость или версию предоставить, какой файл исправить и какую проверку повторить.

Для простой сборки достаточно одного модуля. Состав workspace задаётся схемой, а пути ниже показывают содержимое для анализа и сборки.

```text
project/
  src/main/java/          восстановленные и вручную отредактированные исходники
  src/main/resources/     ресурсы с исходными идентификаторами
  gradle/                 проверенный wrapper и параметры toolchain при экспорте
  build.gradle.kts        шаблон для выбранного профиля
  .bluefaber/             профили, хеши, связи с оригиналом и отчёт импорта
    recovery.json         записи о восстановленных и сохранённых бинарных частях
```

В записи о классе указываются путь в архиве, слой multi-release, двоичное имя, версия class-файла и состояние результата.

| Запись | Что хранится |
| --- | --- |
| Источник | Хеш JAR, путь записи, хеш записи, профиль и достоверность определения платформы. |
| Класс или ресурс | Режим сохранения, путь результата, доказательства сопоставления, статус и связанная диагностика. |
| Зависимость | Объявленный диапазон, найденный артефакт, координаты, репозиторий, хеш и происхождение каждого предположения. |
| Спорное место | Движок и опции, символ JVM, диапазон инструкций, позиция Java, вид ошибки и доступные исправления. |
| Повторяемость | Версии конвейера, схемы, mappings, инструментов и параметры выбранного профиля. |

Примеры машинных причин ошибки — `PROFILE_AMBIGUOUS`, `DEPENDENCY_MISSING`, `CLASS_VERSION_UNSUPPORTED`, `SOURCE_VARIANT_REQUIRED`, `MIXIN_TARGET_CHANGED`. Каждая причина указывает на относящиеся к ней файлы и на ближайшую доступную проверку.

## Архив и метаданные Minecraft

| Объект | Действие |
| --- | --- |
| Дескрипторы платформ и `META-INF/MANIFEST.MF` | Распознать `mcmod.info`, `META-INF/mods.toml`, `META-INF/neoforge.mods.toml`, `fabric.mod.json`, `plugin.yml` и `paper-plugin.yml` в соответствующих профилях. Зафиксировать entry points, параметры загрузки, диапазоны, стороны, зависимости и неизвестные ключи. |
| Mixin, refmaps и доступ | Индексировать конфигурации, refmaps, расширения, Access Widener или Class Tweaker, Access Transformer и исторические трансформеры. Сохранять оригинальные файлы. Для нового профиля обновлять имена структурно и регенерировать производные файлы штатным инструментом. [Миграция Mixin](PORTING.md) |
| `META-INF/services`, Maven-метаданные, ресурсы | Соотносить сервисы с classpath, читать `pom.properties` и `pom.xml` как подсказки, отслеживать пути, порядок при слиянии service providers и конфликты ресурсов. Хранить байтовое содержимое нераспознанных файлов. |
| Вложенные JAR и shading | Отличать объявленные jar-in-jar от классов, скопированных или перемещённых в архив при сборке. Вести происхождение и явный план упаковки. Исключать дублирование классов при восстановлении зависимости из отдельного артефакта. |
| Multi-release JAR и модули | Сохранять базовый слой и `META-INF/versions/<N>`. Выбирать класс по правилам целевой Java только при объявленном multi-release режиме. Сохранять `module-info.class`, сведения о сервисах и модульных границах. |
| Подписи и нативные библиотеки | Хранить исходный подписанный JAR отдельно. После изменения содержимого убрать устаревшие записи подписей из экспорта и при необходимости выполнить отдельную подпись. Указать архитектуру и ОС для нативных библиотек, JNI оставлять явной внешней границей. |
| Пакеты ресурсов и данных | Вести список моделей, текстур, переводов, звуков, рецептов, лута, структур, тегов и `pack.mcmeta`. Изменения форматов, идентификаторов и сохранений проверять правилами целевой версии. |

Для текстовых дескрипторов сохранять неизвестные поля при обновлении. Для бинарных ресурсов фиксировать хеш и изменения по каждому пути. Политика обработки дубликатов должна давать один и тот же результат при повторном запуске. [Спецификация JAR](https://docs.oracle.com/en/java/javase/26/docs/specs/jar/jar.html), [метаданные Fabric Loader](https://docs.fabricmc.net/develop/loader/fabric-mod-json), [Forge mod files](https://docs.minecraftforge.net/en/1.20.x/gettingstarted/modfiles/), [NeoForge mod files](https://docs.neoforged.net/docs/gettingstarted/modfiles/), [plugin.yml](https://docs.papermc.io/paper/dev/plugin-yml/), [Paper plugins](https://docs.papermc.io/paper/dev/getting-started/paper-plugins/)

## Язык Java и JVM

| Проверочный набор | Что сохранить или проверить |
| --- | --- |
| Сигнатуры и совместимость | Generics, bounds и wildcards, erasure, bridge и synthetic, ковариантный возврат, перегрузки, boxing, varargs, type-use annotations. Проверять JVM-дескрипторы, доступность и разрешение вызова в обоих classpath. |
| Инициализация и области видимости | Цепочки `this` и `super`, порядок `<init>` и `<clinit>`, default methods, shadowing, захваченные переменные, локальные и анонимные классы, nestmates. Инициализация может иметь побочные эффекты и исключения. |
| Поток управления | Циклы и метки, switch и fall-through, early return, `try/finally`, try-with-resources, подавленные исключения, `synchronized`, JVM monitor, exception table и исторический `jsr/ret`. CFG сохраняет обычные и исключительные переходы. |
| Вычисления | Последовательность вычисления слева направо, короткое замыкание, изменения состояния, порядок исключений, `null`, casts, типы чисел, переполнение, signed zero, NaN, identity и equality. Проверять эквивалентность реализации узла конкретному поведению. |
| Динамические точки вызова | Лямбды и method references, конкатенация строк, bootstrap handles, `invokedynamic` и `ConstantDynamic`. Неизвестные bootstrap методы остаются байткодом или явным внешним вызовом с диагностикой. |
| Современный и исторический Java | Различать major/minor class-файла, исходный язык и целевой профиль. Покрыть records, sealed classes, pattern matching, switch expressions, preview, старые patterns синтетического кода и разные компиляторы. Обратный порт проверяет наличие API и требуемое поведение отдельно от синтаксиса. |
| Связывание во время исполнения | `Class.forName`, reflection, MethodHandles, сервисы, сериализация, динамические загрузчики и JNI. Вести возможные связи и зависимые имена с уровнями уверенности. Преобразовывать строковые ссылки только по правилам распознанного формата или после явной правки. |
| Другие JVM-языки | Учитывать Kotlin `@Metadata`, его синтетические методы и корутины, Scala metadata и TASTy, динамику Groovy. Java-представление этих классов может помочь чтению. Сохранять бинарные границы и отдельный язык сборки, когда он известен. [Kotlin Metadata JVM](https://kotlinlang.org/docs/metadata-jvm.html) |

Модель потока содержит типизированные значения, блоки, обычные и исключительные рёбра, порядок побочных эффектов и источники инструкций. При загрузке класса ASM читает метаданные и байткод, а закреплённый `javac` проверяет связывание восстановленного Java под конкретным профилем. AST полезен для навигации, анализа исходников и локальной правки. Для импортов с неполным classpath сохраняем неизвестный тип и требование к зависимости. [ASM](https://asm.ow2.io/), [JavacTask и Compiler Tree API](https://docs.oracle.com/en/java/javase/26/docs/api/jdk.compiler/com/sun/source/util/package-summary.html), [JavaParser](https://github.com/javaparser/javaparser)

### Сценарии для регрессий

1. Сравнить результат, исключения и порядок записи состояния для метода с `try-with-resources`, несколькими `return` и исключением при закрытии ресурса.
2. Собрать один и тот же вызов для двух классов с перегрузками, ковариантными результатами и bridge. Сравнить полное связывание вызова и виртуальную диспетчеризацию.
3. Сравнить class-файлы из javac и Eclipse ECJ для вложенных классов и захватов. Повторить с выключенными debug-атрибутами, а затем удалить необязательную зависимость и проверить адресную диагностику.
4. Открыть один multi-release JAR под двумя JDK и проверить выбор слоя. Переименовать класс с распознанной декларативной ссылкой и проверить согласованное изменение манифеста и сервисного файла.
5. Перенести Mixin с двумя совпадениями точки внедрения. При изменении их порядка сравнить цель и действие инъекции на уровне байткода и поведения. Проверить случай, где оба совпадения формально допустимы и требуется решение пользователя. [Сопоставление точек Mixin](PORTING.md)

## От байткода к редактируемым фрагментам

- Сначала показывать ссылки на оригинальные записи, классы, методы и готовый Java. Привязывать узел к полному символу JVM и диапазону инструкций. Для ресурсов указывать файл и ключ. Невосстановленное имя переменной получать из роли или номера слота и явно отмечать как сгенерированное.
- Поднимать команду, событие или операцию над игровым API из сочетания сигнатур, типов, CFG и условий известного адаптера. Проверять владение потоком, исключительные переходы, побочные эффекты и порядок аргументов. Поддерживать обратную навигацию от узла до места в байткоде и к файлу сборки.
- Оставлять сложную функцию вызовом Java, если её интерфейс определён. Если требуется сохранить исходный байткод, считать такую единицу неизменяемой и разрешать перенос лишь для подтверждённого бинарного профиля или проверенного remap. Вложенные классы, synthetic, nestmates и ссылки на ресурсы могут заставить переносить единицу целиком.
- Сначала формировать предложение с изменениями, происхождением и диагностикой. После принятия владельцем поведения становится граф или внешний файл Java. Проверять отсутствие повторной регистрации и дублирующих реализаций. У нарушенной связи отображать источник и причину ошибки.

## Выбор движка и приёмка

Начальная реализация использует Vineflower как библиотеку в отдельном процессе, CFR как запасной движок для отдельных единиц компиляции и Procyon как дополнительного кандидата на стенде. Обновлять движок через набор сравнения. Сначала устранять ошибки зависимостей и mappings, затем проверять конфигурацию движка и независимый резерв. Если отдельный дефект стабильно воспроизводится в нескольких типах модов, подготовить минимальную фикстуру и исправление upstream. Временно поддерживаемый форк допустим, когда исправление проверено и установлен срок пересмотра. [Vineflower](https://github.com/Vineflower/vineflower), [CFR](https://github.com/leibnitz27/cfr), [Procyon](https://github.com/mstrobel/procyon), [сравнительное исследование Java-декомпиляторов](https://arxiv.org/abs/2005.11315)

| Приёмка | Критерий |
| --- | --- |
| Покрытие архива | Каждый класс, ресурс и вложенный артефакт учтён. Любая потеря, замена, перенос байткода или синтетическая правка отражается в отчёте. |

Корпус включает небольшие собственные проекты с известным поведением, открытые пары JAR и исходников с проверенными условиями использования, сборки с отладочной информацией и без неё, разные компиляторы и языки, обфусцированные фикстуры и неполный classpath. Проверять весь класс и проект, поскольку показатель «число файлов без синтаксических ошибок» не выявляет поведенческие и межклассовые расхождения. ### Протокол сравнения

1. Закрепить точные версии движков и наборов входов. Создать эталонные сборки с фиксированными JDK и опциями компилятора. Для сравнительных результатов хранить режим сборки, ожидаемый результат и хеш файла.
2. Запускать основной и запасной движки на одном classpath. Измерять парсинг и компиляцию по единицам, а затем пересобирать рабочий проект без исходного JAR в classpath. Оригинальные классы для диагностики можно использовать лишь в явно отмеченном режиме.
3. Сравнить ключевые сигнатуры, загрузку, ресурсы, работу Mixin и сценарии игры. При обнаружении расхождения хранить пример отдельно. Эталонные тесты проверяют выбранное поведение и не доказывают эквивалентность для всех входов.
4. Сравнить долю успешных полных пересборок и p95 отдельа для поддерживаемых примеров, исторических профилей, смешанных языков и обфусцированных входов. Оставлять метрики по всем группам видимыми, чтобы современные простые проекты не скрыли провал исторического импорта.
5. Записывать причину выбора движка для каждой единицы. При обновлении фиксировать список новых регрессий и успешных случаев до смены основной версии.

### Выполненная проба декомпиляции

В Eclipse Temurin `17.0.17+10` один небольшой Java-пример был собран с `javac --release 17` в двух вариантах, `-g` и `-g:none`. В примере были bridge-метод из обобщённого интерфейса, вложенные типы, sealed-интерфейс и record, лямбда с захватом и подавленное исключение из try-with-resources. [Vineflower 1.11.1](https://github.com/Vineflower/vineflower/releases/tag/1.11.1) и [CFR 0.152](https://github.com/leibnitz27/cfr/releases/tag/0.152) обработали оба JAR. Восстановленный Java во всех четырёх комбинациях собрался с `javac --release 17 -proc:none` без оригинального JAR и дал ожидаемый вывод `12|body/close`. Проверка охватывает только синтетический пример. Для Minecraft, Mixin, обфускации и производительности требуется описанный выше корпус.

## Повторяемая сборка и производительность

- **JDK и входные артефакты.** Различать JDK работника, JVM Gradle, toolchain для компиляции и Java запуска игры. Закреплять точные версии и контрольные суммы Gradle, плагинов сборки, зависимостей, mappings и декомпиляторов. Брать игровые файлы из источников профиля и записывать их происхождение. [Gradle Toolchains](https://docs.gradle.org/current/userguide/toolchains.html), [Gradle Dependency Locking](https://docs.gradle.org/current/userguide/dependency_locking.html), [Gradle Wrapper](https://docs.gradle.org/current/userguide/gradle_wrapper.html)
- **Импорт и выполнение.** Импорт разбирает данные статически и не выполняет импортированные скрипты, annotation processors, модовые entry points и Mixin-плагины. Первичную диагностику Java запускать с `-proc:none`, если профиль допускает такой режим. Полная разрешённая сборка, загрузка игры и испытания используют изолированную рабочую среду, отдельный каталог Gradle, ограничение ресурсов и отсутствие пользовательских учётных данных. Зависимости загружает разрешённая стадия подготовки окружения.
- **Кэш и параллелизм.** Ключ расчёта включает хеш входной единицы, профиль, движок с опциями, JDK и хеши используемых mappings и classpath. Кэшировать инвентарь и проверенные результаты, загружать большие графы по требованию. Размер пула выбирать по памяти с верхним лимитом. Запуск CFR по требованию, отмена по единицам и очистка незавершённого результата снижают стоимость повторной попытки.
- **Замеры.** Собирать p50/p95 холодного и тёплого импорта, пиковую память, объём кэша, задержку отмены и время пересборки после локального изменения. Закреплять оборудование, режим и версии. Выбрать измеримые бюджеты по первому воспроизводимому прогону. Отдельно отмечать пропуски из-за лимита и ошибки восстановления.

Рабочий демонстратор принимает исходники и JAR одного небольшого серверного мода или плагина, показывает происхождение Java и узлов, открывает смешанный проект и воспроизводит его поведение на исходной цели после пересборки. Второй профиль проверяет, что распознанные части действительно переносимы, а точные причины блокировки остальных частей видны до запуска игры. [Критерии этапов 05–08](ROADMAP.md)
